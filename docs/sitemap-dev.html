stack

Elección optimizada para un equipo chico, entrega rápida y una UI muy cuidada. Todo Blade — sin build de SPA, sin API duplicada, sin estado sincronizado a mano.

SDK y modelo

ÍtemValorNotas
Paquetecomposer require "anthropic-ai/sdk"SDK oficial de Anthropic para PHP.
Modelo por defectoclaude-opus-51M contexto · 128K salida. Es el modelo actual recomendado.
Precio$5 / MTok entrada · $25 / MTok salidaCon prompt caching, la lectura de caché cuesta ~0.1× de la entrada.
Alternativa más barataclaude-sonnet-5 — $3 / $15 por MTokDecisión de negocio, no técnica. Vale medir calidad en las piezas reales antes de bajar.
Tareas trivialesclaude-haiku-4-5 — $1 / $5 por MTokSolo para clasificación / etiquetado interno, no para copy de cara al cliente.
ThinkingEncendido por defecto en Opus 5max_tokens limita thinking + respuesta. Dimensionar con holgura.
Effortoutput_config: ['effort' => 'high']Empezar en high y barrer hacia abajo — en Opus 5, low/medium rinden muy bien y son la palanca real de costo.
Streaming$client->messages->createStream(...)Obligatorio: max_tokens alto sin streaming se cae por timeout HTTP.
Salida estructuradaoutputConfig: ['format' => [...]]Para el cronopost, que debe volver como JSON parseable. No usar prefill — devuelve 400.
Prompt cachingcacheControl: ['type' => 'ephemeral']El contexto de marca es idéntico entre peticiones del mismo cliente → cachearlo. Mínimo 512 tokens en Opus 5.
Reglas duras del API — romperlas devuelve 400, no un warning:
  • · temperature, top_p, top_k no se aceptan en Opus 5. Se dirige con prompt, no con sampling.
  • · budget_tokens fue eliminado. Se usa effort.
  • · Nada de prefill (último turno assistant) para forzar JSON — usar salida estructurada.
  • · Revisar stop_reason === 'refusal' antes de leer content[0], o el código revienta cuando un clasificador rechaza.

Anatomía del prompt

construcción del request — BrandContextBuilder
1 · system (cacheado)Identidad de Breakfast + los do's/don'ts de la marca, literales del deck.
"Habla desde la experiencia y el análisis. Nada de lenguaje marketero vacío, exceso de emojis, ni frases motivacionales genéricas. No expliques todo como si el usuario no entendiera. Estética limpia y editorial."
Estable → cache_control: ephemeral
2 · contexto de marca (cacheado)brand_strategies del cliente serializado: personalidad, tono, audiencia, arquetipo, pilares, qué NO decir, campaña vigente. Idéntico entre peticiones del mismo cliente → segundo breakpoint de caché aquí.
3 · plantilla del tipo de contenidoInstrucciones específicas por canal + formato. Reel de IG ≠ copy web. Vive en config/ai/templates/*.php, versionada en git.
4 · brief del usuario (volátil)Va al final, después del último breakpoint de caché. Es lo único que cambia entre peticiones.
system BKF+ contexto marca↤ cache breakpoint plantilla+ brief→ Claude

pagos

El brief menciona una app propia llamada goshop que ya acepta pagos vía Stripe. Recomendación: integrar Stripe directo con Laravel Cashier, no a través de goshop.

Por qué Cashier directo

  • Suscripciones recurrentes, prorrateos, reintentos de cobro y dunning ya resueltos
  • Portal de facturación de Stripe: el cliente cambia tarjeta sin que BKF escriba UI
  • Webhooks firmados y verificados por el paquete
  • Estado de suscripción consultable con $client->subscribed('portal') → middleware directo
  • Un intermediario más es un punto más de fallo para el cobro automático

Dónde sí usar goshop

  • Si la cuenta de Stripe ya vive dentro de goshop y no se puede separar, se reutiliza esa cuenta — pero conectando Cashier a ella, no llamando a goshop
  • Cobros puntuales fuera de suscripción (talleres sueltos, extras)
  • Vale confirmar con el cliente antes de decidir: es la única pieza del brief donde falta información técnica
MVP: sin cobro→ plan free forzado→ al salir de MVP: Checkout→ webhook→ middleware subscribed

Construir el modelo de suscripción desde el día 1 aunque no se cobre: el plan free es una fila en plans, no un if desperdigado por el código. Cuando llegue el momento de cobrar, solo se cambia el precio.

roles & autorización

Roles (spatie/laravel-permission)

  • admin — BKF, todo
  • equipo — BKF, sin back-office financiero
  • cliente_owner — dueño de la marca: factura, invita usuarios
  • cliente_miembro — usa el portal y el IA Studio, no ve facturación

Reglas no negociables

  • Global scope por client_id en todo modelo del portal
  • Policy en cada recurso, no solo middleware de ruta
  • Descargas siempre por controller con can:view, nunca link directo a S3
  • El contexto de marca que va a Claude se resuelve del usuario autenticado, nunca de un parámetro del request
  • Test de fuga: un cliente no puede leer datos de otro ni por ID directo
